# 凌晨两点排障四十分钟后，我把这套流程做成了一个开源工具

> 如果你也维护过一天几百万条日志的系统，应该懂那种"信息明明都在，但你就是看不见"的无力感。

先说结论：我做了个开源的日志根因分析工具，叫 **LogPilot**。它把日志先聚类成模板，再用规则和 LLM 找出根因。

但我想聊的不是这个工具，而是它为什么长成现在这个样子——**中间有几个决定，和我一开始想的完全不一样。**

---

## 一、那次排障，四十分钟

告警响了：巡检平台大量任务超时。

三个微服务，两台服务器。我登录上去，做的第一件事和大多数人一样：

```
grep "ERROR" app.log | tail -100
```

翻了四十分钟，才定位到是 Redis 连接被占满，缓存全部击穿，请求打到了数据库。

故障本身不复杂，难受的是过程：**有用的信息一直在日志里，只是没人能在几百万行里一眼看出来。**

后来我在公司写了个脚本，把巡检日志接进 AI 工具链做初步分类。效果不错，但它长在内网里，换个人就用不了。

于是我想：能不能把它做成一个谁都能跑的东西？

## 二、第一反应是错的

我最初的方案特别简单：日志直接丢给大模型，问它根因。

试完才发现三个问题，一个比一个硬：

**第一，钱。** 一次几千 token，几分到几毛。一天几十次告警，一个月是真金白银。

**第二，幻觉。** 它会一本正经地编造日志里根本没出现的服务名。你信了，就排查到沟里去了。

**第三，慢。** 8 到 15 秒。在告警场景里，这十几秒比你想象的长得多。

结论：**日志不能原样喂给模型。**

但为什么呢？我后来想明白了——一百万条日志里，可能只有五十种"形状"。人看不出来，因为每条的时间、ID、IP 都不一样；机器也看不出来，因为它不知道哪些部分是变量。

**所以真正该做的，不是让模型读更多日志，而是先让人和模型都"看见形状"。**

## 三、先把日志压成模板

这一步用了经典的 Drain 算法（2017 年的一篇论文），核心就三步：

1. 按 token 数量分层，不同长度的日志不互相比
2. 逐 token 比较，相似度超过阈值就合并
3. 不一致的位置替换成通配符

效果是这样：

```
原始：Connection to 10.0.0.11:8080 failed after 3000ms
原始：Connection to 10.0.0.12:8080 failed after 5120ms
模板：Connection to <*> failed after <*>ms
```

我实测的样例：**30 条日志，压成 17 个模板**。真实场景压缩比通常在一百比一以上。

这一步做完，喂给模型的东西就变了。原来是一坨文本，现在是一张统计表：

```
1. [5 次] order <*> created, userId=<*>, amount=<*>
2. [4 次] Connection to <*> failed after <*>ms
3. [3 次] Slow query detected: select * from t_order where id = <*> took <*>ms
```

**模型看到的不再是日志，而是"哪种形状在突增"。**

而"突增"这件事，恰恰是原始日志里最看不出来的信号。

这里我做了个取舍：论文里的固定深度前缀树我没实现，改成同长度桶里线性扫描。因为模板数量在千级以内时，线性扫描完全够用，而代码量从五百行降到一百行。

**能让别人读懂，比性能多几个纳秒重要。** 这句话我后来越来越信。

## 四、规则和 LLM，不是二选一

聚类解决了成本，但没解决可靠性。所以我最后定的是：**规则先行，LLM 增强。**

理由很朴素：

- OOM、连接被拒、慢 SQL、连接池耗尽、磁盘满——这些**已知故障**，一条正则就能判，零成本、零延迟、结果还稳定。让模型去判，纯属浪费。
- 规则覆盖不到的、需要跨模板推理的**未知故障**，才是模型的主场。

执行顺序是刻意设计的：

```
1. 先跑规则 → 拿到一份"一定能交付"的结论
2. 再调 LLM → 成功就覆盖根因、补充证据
3. LLM 挂了 → 只让报告标记"降级"，规则结论照样出
```

**接口永远不会因为模型挂了返回 500。** 这条底线，比多识别一种故障模式重要得多。

## 五、真正让我花时间的，是"坏了怎么办"

功能两天就写完了，剩下的时间全花在降级上。这部分没人会夸你，但它是系统能不能用的分界线。

**LLM 不可用**时，报告会给三个字段说清楚走了哪条路：

```
{ "degraded": false, "llmModel": "deepseek-chat", "degradedReason": null }
{ "degraded": true,  "degradedReason": "LLM 调用失败：Connection refused" }
```

"没配 Key"和"调不通"必须分开——因为这两种情况的排查动作完全不同。

**Redis 不可用**时，我做了个熔断，三十秒内不再重试。所有操作都包了一层，失败时的返回值是仔细想过的：

```
去重失败 → 当作"没见过的"，宁可多存也不丢日志
加锁失败 → 当作"拿到锁的"，宁可多做一次也不卡用户
```

这两个默认值值得多说一句：**去重失效的代价是多写几条数据，丢日志的代价是排障时缺证据。** 两害相权，宁可多存。

**模型返回不合法 JSON** 时，截取第一个花括号到最后一个花括号。还解析不了，就当这次没有结果。

不允许"尽力猜"。**猜错的根因比没有根因更危险。**

## 六、几个踩出来的坑

写代码的时候没人告诉你这些，踩一次记一辈子。

**H2 文件库被强杀后会锁成只读。** 开发时 Ctrl+C 杀进程，下次启动直接报 `The database is read only`。后来默认库换成内存模式——开发环境的首要目标是"永远能干净启动"，不是"数据不能丢"。

**容器里的 JVM 不知道自己被限制了多少内存。** 宿主机 32G，容器限制 768M，JVM 默认堆敢按宿主机算到 8G，一跑就被 OOM Kill。所以 Dockerfile 里必须显式写死 `-Xmx512m`。

**日志指纹不能用 `String.hashCode()`。** 它是 32 位，几十万条日志下冲突率不可忽略。而**冲突意味着两条不同的日志被当成重复丢掉**——排障时丢证据是致命的。换成 SHA-256。

**Windows 批处理别写中文注释。** `.cmd` 是 UTF-8，但 cmd 按 GBK 解析，中文注释会把整行拆成命令，报 `'避免终端默认' is not recognized`。我盯着这个报错笑了很久。

## 七、我特意"没做"的事

这部分可能比"做了什么"更能说明问题。

**没用 Elasticsearch。** 我说过它内存吃得多——2G 的机器根本起不来。MVP 阶段用 MySQL 聚合完全够。

**没拆微服务。** 三个模块足够讲清架构，拆成九个只会让你跑不起来。**开源项目跑不起来，star 就是零。**

**K8s 里固定 1 个副本。** 因为模板状态在 JVM 内存里，多副本会各算各的，同一个服务在不同 Pod 上结果不一样。

我把这句话写进了部署文档：

> 要水平扩展，得先把模板状态外置到 Redis。在此之前不要调大副本数。
> **宁可部署得保守，也不要一个看起来能扩展、结果却不对的系统。**

一个"能扩容但结果是错的"系统，比"暂时不能扩容"危险十倍。

## 八、最后

项目叫 LogPilot，Java 17 + Spring Boot 3，Drain 聚类 + 规则引擎 + LLM 归因，Docker 一键起，15 个测试。

**没有 API Key 也能完整演示**——我在仓库里放了假的 LLM 服务和假的 Redis，演示的时候不用花钱、不用联网。

仓库地址在评论区置顶（知乎对外链有限制，见谅）。

---

做这个项目最大的收获，其实不是学会了怎么调模型接口。

而是想明白了一件事：

**AI 能让一个功能变聪明，但让系统能用的，永远是那些"出错了怎么办"的设计。**

规则兜底、超时降级、熔断、幂等、可观测——这些老掉牙的东西，在 AI 时代一个都没少，反而更重要了。

因为你的系统里，多了一个**会超时、会胡说、还按 token 收费**的组件。

---
